# 운영팀 회의 TODO 일일 파이프라인

상태: 코드 구현 및 모의 API 테스트 완료 · 운영 Cron 배포 전

## 실행

`/ops-reminder -mode daily -send`를 매일 10:00 Asia/Seoul에 **동시 실행 없이** 한 번 실행한다. `-send`가 없으면 Notion과 Discord에 쓰지 않는 미리보기다. `-mode notion-sync -send`는 회의 TODO 생성 단계만 실행하며 Discord 발송·현재 회의록 체크 변경을 하지 않는다. 이전의 `d1`, `meeting-followup` 명령은 호환용으로 남겨두지만 운영 스케줄에는 사용하지 않는다. 이미지 배포용 GitHub Actions 일정은 이 TODO 실행 일정과 다르다.

실행 순서는 다음 네 단계다.

1. **회의 선택:** 운영팀 회의록 DB의 `Date` 속성으로 오늘보다 이전인 가장 최근 회의와 오늘 또는 이후의 가장 가까운 회의를 찾는다. `created_time`은 미래 템플릿이 미리 생성돼 있으므로 회의 개최일로 쓰지 않는다. 지난 회의 페이지와 TODO 후보 블록이 회의 날짜 이후에 수정된 경우에만 새 결정 추출을 시도한다. 회의 날짜가 바뀌면 DB의 `Date`를 갱신해야 한다. 다음 회의 페이지가 없으면 쓰기·알림 없이 종료한다.
2. **다음 회의록 TODO 작성:** 지난 회의의 `안건`과 `결론`에서 행동 후보를 추출하고, 부모 안건·장소·프로젝트 문맥 및 연결된 Discord 스레드와 함께 모델이 두 번 검증한다. 최종 모델 출력의 `task_title`은 맥락을 드러내는 짧은 행동 문장이다. 실제 미완료 작업만 다음 회의록의 `결론` 바로 뒤에 `## TODO` 토글 제목으로 만든다. 그 아래 담당자별 글머리표를 두고 한 단계 들여쓴 Notion `to_do` 블록에 요약 제목과 기한을 쓴다. 명시적 기한이 없으면 `기한: 다음 회의 전 (회의록에 데드라인을 명시해주세요)`로 적고, 내부 발송 날짜는 현재 다음 회의록 `Date`를 사용한다. `출처` 링크는 원본 회의록의 해당 블록을 가리키며, 연결된 스레드가 있으면 `스레드` 링크도 붙인다. 원본 ID를 화면에 텍스트로 표시하지 않는다. 재실행 시 출처 링크를 대조해 중복 생성을 막는다. 이전 회의록의 미완료 TODO도 다시 확인한 후 다음 회의록으로 이월한다.
3. **완료 상태 갱신:** 현재 대상 회의록의 미체크 TODO마다 원본 링크와 명시적으로 연결된 Discord 스레드를 읽는다. 원본 메시지 또는 스레드 내부의 커스텀 `Done` 반응(ID `1501195973865640040`)은 완료로 처리한다. 그 외에는 두 번의 모델 판정이 실제 Discord 메시지를 근거로 완료 또는 취소를 확정한 경우에만 체크한다. 불확실하면 체크하지 않고 미완료로 둔다. 별도의 `확인 필요` 표시·메시지는 만들지 않는다. 사람이 체크한 블록은 다시 해제하지 않는다.
4. **리마인더 발송:** 다음 회의 날짜가 내일이거나 TODO의 기한이 내일인 경우, 그 시점에 미체크인 작업만 Discord 대상 채널로 보낸다. 두 조건이 동시에 참이어도 항목별로 한 번만 보낸다. `members.json`에서 확인된 담당자만 `allowed_mentions`로 멘션한다. Discord는 `<@사용자ID>`를 화면에서 사용자 이름 멘션으로 렌더링한다. 작업 제목 자체를 Notion TODO로 연결하는 마스킹 링크를 사용하므로 별도의 `근거` 줄은 없다. 동일한 본문의 봇 메시지가 있으면 재전송하지 않는다. 전송 결과가 불명확하면 채널을 재조회하고 중단한다.

```text
결론
## TODO  (토글 제목)
- 김찬우
  ☐ 스위프 파트너십 거절 메일 작성 · 기한: 다음 회의 전 (회의록에 데드라인을 명시해주세요) · 출처 · 스레드
- 담당 미정
  ☐ 민상렬홀 사용 전 방문 · 기한: 다음 회의 전 (회의록에 데드라인을 명시해주세요) · 출처
```

```text
<@담당자ID> [스위프 파트너십 거절 메일 작성](다음 회의록 TODO 링크)
기한: 다음 회의 전 (2026-11-20)
```

## 판단과 데이터 경계

- 현재는 Notion 회의록 DB와 명시적으로 연결된 Discord 스레드만 읽는다. 연결되지 않은 대화를 제목 유사성만으로 같은 TODO에 연결하지 않는다. 스레드 링크가 없다면 자동 완료 판정에 사용할 Discord 대화도 없다.
- `Done` 반응은 코드가 확인하고, 대화 문맥의 완료·취소는 모델이 판정한다. 모델이 스레드 외의 문장만 인용해 완료라고 하면 체크하지 않는다.
- `다음 회의 전까지`는 실제 다음 회의록의 `Date`를 모델에 전달해 기한을 검증한다. 기한이 없거나 추측성 표현뿐이라면 다음 회의 날짜를 기본값으로 삼되 Notion에 명시 요청 문구를 표시한다. 행사 날짜를 준비 작업의 기한으로 옮기지 않는다. 마감일 변경은 현재 다음 회의록 TODO에 사람이 반영한 값을 기준으로 한다.
- Notion 체크박스는 이 파이프라인의 이진 상태다. 체크는 완료 또는 진행하지 않기로 확정된 작업을 뜻한다. 모델의 판단이 불분명하면 체크하지 않는다.
- 원본 회의록과 다음 회의록의 페이지 및 블록 ID는 내부 API 처리에만 사용한다. 사용자에게는 읽기 쉬운 출처 링크만 표시한다.
- 회의록 페이지가 미리 작성될 수 있으므로 `Date` 이전에 적힌 안건만으로 회의가 끝났다고 추정하지 않는다. 회의 날짜 이후에 수정된 TODO 후보가 없으면 새 결정은 작성하지 않는다. 회의가 실제로 열렸어도 회의록을 갱신하지 않았다면 자동 추출은 다음 실행까지 보류된다.

## 실패와 재실행

Notion·Discord·모델 조회 실패나 페이지네이션 한도 초과는 빈 결과로 처리하지 않는다. 쓰기 실패 뒤에는 다음 실행에서 출처 링크와 체크 상태를 다시 조회한다. 한 실행의 모든 상태 조회가 끝나기 전에는 리마인더를 보내지 않는다. 다만 Notion과 Discord 간 원자적 트랜잭션은 없으므로 CronJob 동시 실행을 금지해야 한다. 최대 후보 60개, Notion 하위 블록 500개, 연결 스레드 3개라는 코드 상한을 유지한다.

배포에는 `NOTION_TOKEN`, `DISCORD_TOKEN` 또는 `DISCORD_TOKEN_FILE`, `OPENROUTER_KEY` 또는 `OPENAI_API_KEY`, 회의록 데이터 소스 ID와 두 Discord 채널 ID를 시크릿·환경변수로 주입한다. Notion 연결에는 회의록 읽기와 대상 페이지의 블록 생성·수정 권한이 필요하다. 토큰과 원문 수집 결과는 공개 저장소에 넣지 않는다. 배포 전에는 읽기 전용 미리보기, 테스트용 회의록 쓰기, 상태 갱신, 실제 Discord 발송을 순서대로 검증한다.

## 배포 준비

`waffle-world-oci/argocd/discord-bot`의 CronJob은 `10:00 Asia/Seoul`, `concurrencyPolicy: Forbid`로 설정한다. 첫 배포에서는 `suspend: true`로 두고 다음 순서로 활성화한다.

1. OCI Vault의 기존 `discord-bot` JSON 시크릿에 `token`, `notion_token`, `openrouter_key` 필드가 있는지 확인한다. JSON 문법이 유효해야 하며 값은 Git에 기록하지 않는다.
2. External Secrets가 Kubernetes `discord-bot` 시크릿을 `Ready=True`로 동기화했고 세 키가 존재하는지 확인한다. 값 자체는 로그에 출력하지 않는다.
3. `dicoco` 이미지에 `/ops-reminder` 실행 파일이 포함되고 GitOps 이미지 태그가 갱신된 것을 확인한다.
4. 읽기 전용 실행과 제한된 실제 동작을 확인한 뒤 CronJob의 `suspend`를 `false`로 바꾼다. 발송 전에 대상 Discord 채널과 멘션 대상도 확인한다.

회의록 데이터 소스 ID, Discord 소스 채널 ID, 발송 채널 ID와 모델 이름은 OCI CronJob의 일반 환경변수다. 이 값들은 인증 시크릿이 아니다. `DISCORD_USER_MAP_JSON`을 지정하지 않으면 저장소의 `members.json`을 사용한다. GitHub Actions의 `OCI_AUTH_TOKEN`, `DEPLOYER_APP_PRIVATE_KEY`는 기존 이미지 배포용 GitHub Secrets이며 새 CronJob의 Vault 항목과 별개다.
